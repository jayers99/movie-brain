# CheapCharts contract — direct links, store ids, Wishlist it (moved from CLAUDE.md 2026-09-21)

- CheapCharts links are DIRECT, not searches. `external_ids` authority `itunes` holds the iTunes track id CheapCharts keys its product page by; `FilmView.cheapcharts_url` derives `https://www.cheapcharts.com/us/itunes/movies/<id>` on every read (never stored, never fetched at render time), and the drawer falls back to today's title-search link only when the id is missing AND the film has a store listing — and `FilmView.apple_tv_url` opens the same product in the Apple TV app. `cheapcharts resolve` was the only writer until 2026-09-20; `cheapcharts wishlist --resolve --apply` is the second (see Wishlist it below) — both believe only an exact IMDb-id answer from CheapCharts, and a film may therefore hold two store ids (`itunes_id_for` and `_VIEW_SQL` both pick `MIN(value)`, so the drawer's link and the wishlisted product agree). The API answers for products Apple has removed (title prefixed `[❌Removed from iTunes]`, `Product.removed`), and both paths treat such a product as a miss; `--recheck` audits stored ids and `replace_external_id` is the only path that changes a stored claim value; its sibling `drop_external_claim` (2026-09-20, claim authorities only) is the only path that REMOVES one, used when a film holds a removed product beside a live one — such a film is asked about product by product (`CheapChartsClient.is_removed`, the same title marker on DetailData), because the by-IMDb answer speaks for one product only and `MIN(value)` had been linking three drawers to products Apple had pulled (report counter `dropped`; two LIVE editions are both kept; unknown is never treated as removed). `itunes` is deliberately NOT in `KEY_AUTHORITIES`: it names a storefront product, not the work — a reissue gets a new track id — so it is a claim and the identity machinery stays blind to it. Two paths in order: `Prices.php?action=getPrices&imdbIDs=` (the on-sale design's §4 "join problem" is OVERTURNED — CheapCharts CAN be keyed by IMDb id, so the iTunes id is an output, not a prerequisite), then `Search.php` for the holes in their IMDb index (Amour has a product page and no IMDb mapping). An IMDb answer naming a product ANOTHER film holds is a miss by IMDb id too (since 2026-09-20 — CheapCharts answers Final Reckoning's tt with Dead Reckoning's page): the search runs, nothing is ever taken from the holder, and only when the search cannot better it is the film counted `held`. A search answer that `match_owned` confirms is still not believed until the PRODUCT's own filing agrees (since 2026-09-20, `CheapChartsClient.filing` over DetailData, `application/cheapcharts.py::_refusal`, in the resolve path and in `--recheck`'s replacement path alike): the same IMDb id is proof, another one is a refusal, with no IMDb filing only an agreeing director will do, and unverifiable is refused — a search result carries no director, and the first `--retry-misses` run stored another film's product on two of three films (The Stranger 2022 twice over; Hope 2013 against an undated Hope). A search answer goes through `match_owned` — a CheapCharts result IS an Apple store title, so the COMMERCE band is the right policy — and two results naming the same film under different track ids are refused as ambiguous rather than guessed. `llms.txt` promises "no rate limiting concerns" and the API answers 429 anyway, so calls are paced (`DELAY_S`) and a 429 raises `RateLimited`, which stops the run; nothing is lost, because the default pass never re-fetches a stored id (only `--recheck` does, and it resumes with `--after`).
- **Wishlist it** (brief `docs/superpowers/briefs/2026-09-19-price-watch/brief.md` — read its Amendments 1.1–1.4 first; plan `docs/superpowers/plans/2026-09-19-wishlist-it.md`; migration 027): the drawer's links row carries one slot after the CheapCharts link — `♡ Wishlist it` on a film that holds an `itunes` id, is not owned and is not wishlisted; `♥ Wishlisted` (itself the un-wishlist button, tooltip `Remove from your CheapCharts wishlist`, no confirm) on a wishlisted film, owned or not; nothing otherwise. A click makes THE SOFTWARE add the film to the owner's CheapCharts wishlist with target = lowest price EVER + $1 (`domain/wishlist.py::target_price`; a one-off low counts — owner ruling; SD and HD targets equal; HD history first, SD when HD is empty, no history = failure), and the row gains a heart (`.icon-wish`, LAST among the badges, tooltip `On your CheapCharts wishlist`). **No price is ever stored or shown**, the on-screen failure is always exactly `Couldn't reach CheapCharts.` + `Try again` (which repeats whichever action failed, remembered on the slot), and busy reads `Reaching CheapCharts…` — those strings are a hard taste boundary. The wishlist LIVES ON CHEAPCHARTS; `cheapcharts_wishlist` (film_id PK, added_on; in `_ONE_ROW_TABLES`, so `merge_film` moves it survivor-wins) is only the local mirror that draws hearts, written by `replace_wishlist` (wholesale, from a read; disposed films excluded; a film is hearted by ANY of its store ids), `mark_wishlisted` and `unmark_wishlisted` and nothing else. **The truth rule (amendment 1.3): every click READS the wishlist first (`application/wishlist.py::_read`, which also refreshes every heart) and nothing is written — to CheapCharts or locally — if that read fails;** a film the read shows already listed WITH a target (`WishlistItem.custom_target`, set by hand or by us) is hearted and its target NEVER touched — this is what protects a hand-set target when local hearts are stale; listed WITHOUT a target (a half-finished click) gets set-target only; an add or remove CheapCharts refuses is a failure; there is no fallback that believes a write without proof. `unwishlist_film` removes every one of the film's products the read holds. Hearts are also refreshed at every `dashboard` start (`cli._refresh_hearts`; CheapCharts being down never stops the start; the line names how many wishlist films are unplaced and the `--resolve` command — that number never reaches zero, because wishlist films not in the catalogue stay unplaced). `infrastructure/cheapcharts.py` holds the adapters: the public `CheapChartsClient.lowest_price` / `imdb_id_for` over `DetailData.php` (`results.movies` is ONE object; `priceHdEvolution` is `~`-joined `date:±price` where the sign is the DIRECTION of the change, never part of the price), a clock-based `Pacer` (1.5 s, shared by both clients — one host), and `CheapChartsAccount` (form POSTs to `Account.php` / `Wishlist.php`; login sends the SHA-256 HEX digest of the password; `itemType` MUST be `buymovies`; token in memory only, one fresh login on a token error). **Answer shapes were learned the hard way: the wishlist READ answers `{results: {ebooks[], movies[], tv[]}, originRequest, responseTimestamp}` with NO `status` key (`idInStore` a string, `customPrice` absent when no target, `initialPriceValue` may be -1) while add / set-target / remove DO answer `status: success|error` — 1,546 green tests and four reviews missed that every read failed, because every fixture had been written from the brief's prose; a fixture for an external answer is built from a real (redacted) answer's shape with invented ids, never from prose.** Secrets: credentials live in `<config_dir>/credentials.toml` (`infrastructure/credentials.py::load_credentials(config, site)`; owner ruling — one file for every site, keyed by site; OMDb/TMDB keys are read from there too since backlog 21, the old key files still working); no credential, token, email, customer id or API message may be printed, logged, fixtured or committed — `CheapChartsError` carries OUR wording only, `_failed` maps a `requests` error to its class name and `RateLimited` to `rate limited`, the 502 routes log only that, and `typer.Typer(pretty_exceptions_show_locals=False)` keeps frame locals out of tracebacks. Rich eats `[cheapcharts]` as markup: a printed literal with square brackets needs `markup=False`. `create_app(..., wishlist: WishlistGateway | None)` — None (no credentials) makes both routes answer the failure line; `POST` / `DELETE /api/films/<id>/wishlist` run under one lock (a click is several paced calls); the web tests drive the routes with fakes through the `PriceSource` / `WishlistAccount` Protocols, so no test can reach a real account. `FilmView.wishlisted` rides on the list payload. Known limits: a film holding two LIVE store ids links the `MIN(value)` product in the drawer whichever one is wishlisted (measured 2026-09-20: two such films, and in neither was the wishlisted product the one skipped); a network blip mid `--resolve --apply` aborts without listing the ids already stored (the next run sees them as held); other rows' hearts refresh on reload, not live.
