# Curated-list contract (spec `docs/superpowers/specs/2026-08-28-curated-lists-design.md`,
  seed `docs/superpowers/specs/2026-08-28-curated-lists-seed.md`, supplied-id increment
  `docs/superpowers/specs/2026-08-28-list-supplied-ids-design.md`, trust + tally increment
  `docs/superpowers/specs/2026-08-29-list-trust-and-tally-design.md`)

- The failure this feature must not produce is a DUPLICATE FILM (seed §0). A list entry is a curator's title plus, usually, a director — no year, no id, no url — so every helper here is deliberately timid: under-creating costs one review row a human drains, over-creating costs a merge. Whenever a gate is unsure, it refuses and queues; it never guesses.
- Two verbs, two deliberate yeses. `movie-brain lists import PATH [--apply]` (`import_list`, design §5) links what the catalog already holds and asks about the rest, and **never creates a film — not on any path, not with `--apply`**. `movie-brain lists create SLUG [--apply] [--yes]` (`create_films`, design §6) is the ONLY path in this feature that creates one, behind its own confirmation. Both are dry-run by default and a dry run writes NOTHING — no registry row, no entries, no claims, no review rows. Both verbs need BOTH an OMDb key and a TMDB token (`session_fetcher` needs both to build a fetcher at all, and a missing token would silently disable gate 2b), and `lists create` checks that BEFORE it prompts: a run that cannot happen must not first ask the owner to authorise it. `create_films` itself refuses outright (exit 1, nothing touched) when handed `tmdb=None`, because gate 2b is not optional on the creating path — the invariant lives in the module that does the creating, not only in the CLI. `import_list` is deliberately left alone: linking without gate 2b is degraded, not dangerous.
- The list file (`lists/<slug>.tsv`, design §4) is a checked-in artifact, extracted once by hand — no scraper, no per-site selectors. `infrastructure/listfile.py::parse_list_file` is pure and keeps titles and directors BYTE-FOR-BYTE: curly apostrophes, `…`, and the source page's own typos (`Howard Hawkes`, `Joseph Mankiewitz`, `Ernst Shoedsack` in `cahiers-100.tsv`) all survive verbatim. A list is a historical record of what the curator wrote; the resolver matches on title and treats the director as corroboration, never as an exact key, so a typo is not a defect to fix. Header block is `# key: value` before the first data row (`slug`/`name` required, `ordered` defaults true); data rows are `printed rank<TAB>title<TAB>director` plus an optional fourth `tt` column and an optional fifth `year` column (migration 020's `year_listed`, four digits verbatim, a cell of spaces is empty — for the title-and-year sources that print no director: List Obsession's slapstick 200 came in this way, Rotten Tomatoes' noir 100 could). `read_list_file` is the one I/O function.
- Column one of the file is the rank AS PRINTED (tied-ranks design §3), not the addressable thing — a critics' poll ties most of its ranks (BFI 2022: 233 of 273 tokens, `=243` alone covers 22 films), so `film_list_entry.rank` means the entry's LINE ORDER, 1..N, and stays what makes an entry addressable (the primary key, `film_rank_on_list`, every `<slug>#<rank>` review-row value). `rank_label` (migration 015, `film_list_entry.rank_label TEXT`, additive, no backfill) carries the printed cell and is stored ONLY when it differs from `str(rank)` — so `1, 2, 3…` stores `NULL` throughout and ties store their own printed form (`=243`). A label parses as an optional leading `=` then a positive integer and nothing else (`_RANK_LABEL_RE`) — no leading zeros, no bare `=`, no trailing text — same `ListFileError` treatment as a malformed id.
- The non-decreasing check on the labels' numeric parts replaces the old duplicate-rank guard, and the replacement is deliberate, not incidental: position is now derived from line order, so gaps and duplicates in column one can no longer corrupt it, which means the old guard was protecting nothing. What it's replaced with catches the mistake THIS feature invites — the BFI page defaults to listing 250 → 1, so an extraction that forgets to reverse the page order now fails loudly (`rank went backwards`) instead of silently importing a poll upside down. What column one no longer protects is position STABILITY: when rank came FROM column one, a hand-extraction that dropped a line left every remaining entry at its printed rank, and now one omitted line renumbers every entry below it. That compounds — `upsert_list_entry` never clears `film_id` and `import_list` short-circuits on the stored rank — so re-importing a corrected file after entries have linked would keep every stale link while overwriting its title, a silent mislink reported on the card as `already linked`. Hence the rule: **a list file is APPEND-ONLY once imported**, and a mid-file correction means re-verifying the links, not just re-running the import (design §6 puts re-ordering out of scope for the same reason). `entry-changed` is what enforces it — when a stored entry's `title_listed` no longer matches the file's at that rank, the entry is NOT settled: the row queues, naming both titles, and the existing link is left exactly where it is. The comparison is exact equality on the title alone — a director typo or a newly added `tt` is a legitimate edit, not a renumbering.
- A tie is a display fact, not an identity fact: it touches no gate, no reconciliation path, and no review-row value — `<slug>#<rank>` is built from the position exactly as before, and `film_rank_on_list`'s duplicate-entry guard still answers in positions, which stay unique even when their labels don't. The drawer and the scorecard both render `rank_label` when present, else `rank` (`app.js`'s `l.rank_label ?? l.rank`, `scorecard`'s explicit `r.rank_label is not None` check, not a falsy-`or`, so a future non-parser producer of `rank_label` can't silently fall back to the position) — an unordered list still shows no rank at all either way. `cahiers-100.tsv` and `bergan-100.tsv` print `1..100` in line order, which is already their rank, so all 200 of their rows store `rank_label = NULL` and parse and render exactly as they did before this feature.
- The form ladder (`resolve_entry`, design §1 A2) is FALLBACK-ONLY: the primary form is asked first and a `match` there returns immediately — a form further down the ladder can never override an already-corroborated primary match. Only when the primary misses are `base` and then each alt title tried, stopping at the first `match`. When nothing matches, the PRIMARY form's verdict is what comes back (it was asked against the title the curator actually wrote, so its reason is the one worth reviewing), or the first form that answered when the primary's own lookup failed; when every lookup failed, `(None, primary_form)` — a transient failure is not a verdict and must never become a durable review row. The query year is the LISTED year when the file prints one (fifth column) and `None` otherwise — never a year embedded in the title, and never invented: a curator's printed year is the work's year, so `make_query` gives a `list` query the DATABASE year class (trusted like the catalog's own, not the remaster-prone commerce class), and it corroborates exactly as the director does. That is what makes a director-less source importable at all: before it, 81 of Rotten Tomatoes' 100 noirs came back `weak` (Laura 1944 vs 1979 and every other remade title). `lists create` re-resolves from the STORED entry, which is why the year is a column and not just a file cell. `entry_forms` is the ONE definition of "what might this entry be called?", shared by the ladder in both verbs. Gate 3 asks a DIFFERENT question — "what will the catalog GAIN?" — and **both** verbs veto over the entry's forms PLUS the winning candidate's own titles, through the one shared `veto_forms(forms, winner)`. The two questions stop having the same answer the moment phase 2 mints the film under TMDB's title rather than the curator's: a legacy unkeyed row titled like the winner holds no ids (gates 1/2/2b all miss it) and is titled nothing like the listed entry (the listed forms miss it too), leaving `films.key` — which refuses only when title AND year both match — as the sole backstop. The two vetoes are deliberately IDENTICAL and must stay so: `import_list` creates nothing either way, so the wider veto there only moves an entry from `would-create` to `blocked` plus a review row, and it moves it onto the rehearsal card the owner authorises FROM rather than leaving the card promising a creation the confirmed run would refuse. Strictly in the refusing direction, the same argument design §1 A4 makes for gate 2b. (The asymmetry between the verbs is the `tmdb is None` guard below, and only that.)
- Three gates before any creation, plus gate 2b (design §5.5, §1 A4). Gate 1: a film already keyed to the winning IMDb id. Gate 2: a film holding the winning candidate's TMDB id. Gate 2b: when gate 2 asked nothing — the winner is OMDb-only and carries no TMDB id, or `resolve` truncated `ranked` to three and the winner fell outside it — `tmdb.find_by_imdb(verdict.tt)` supplies the mapping and the holder is looked up on that. Gate 2b's only input is `verdict.tt`, never the winner. Gate 3 (`corpus_veto`): every catalog film RESEMBLING any of the entry's forms, which is a veto and not a matcher — a weak, ambiguous or tied hit is reason enough to refuse, deliberately inverting `owned import`, where the corpus matcher is a fallback that picks a winner. `find_holder`'s labels (`imdb tt…`, `tmdb N`, `tmdb(find N)`, `tombstoned #N`, `no holder`, `tmdb lookup failed`, `""`) are contract text the scorecard prints and callers branch on. A gate 2b RAISE is `error`, never `would-create`: the holder is unknown, not disproved, and calling it a would-create points phase 2 at a film that may already exist.
- `create_films` re-resolves and re-gates EVERY entry — phase 1's verdict is never trusted, the same re-derive-at-resolution-time rule the repair verbs follow. Its worklist is every entry with no `film_id` and NO `list` review row for its `<slug>#<rank>`, open or resolved: either kind means a human owns that entry. A film is minted under the WINNER's title and year (TMDB's own), with the listed title kept verbatim in the `claim` row, and is keyed immediately through `key_film` — born keyed, exactly as Mode-B promotion does it. A keying failure never undoes a creation that already happened; the next sync retries. Two consequences of that, both intended and neither obvious: (a) `list` is NOT in `application/thumbprint.py::_CLAIM_PRECEDENCE`, so a `list` claim never drives `film_query` — a list-created film that fails keying is re-queried by the next sync under its OWN (the winner's) title, not the curator's, and a reader of `thumbprint.md`'s "every ingester writes its own claim row at ingest" should not assume the claim participates in resolution; (b) `_key_new_film` SWALLOWS `key_film`'s `[partial]` `RuntimeError` where `repair editions` and `repair nomatch` raise and exit 1 — the deliberate exception to `thumbprint.md`'s loud-stop rule, because one entry must not abort a 100-entry run, and it is safe because the only non-`KEYED_OK` result is `id-conflict` and `record_tmdb_match` has already queued a durable `id-conflict` review row naming the twin before raising. Beyond the three gates, creation refuses on a tombstoned `films.key`, on a `films.key` collision `create_film` reports (never adopt the clashing film — that is how a wrong link is made), and on a `tt` this same run already minted (`minted`, which the gates structurally cannot stand in for: an unkeyed new film holds no external ids and is indexed under the winner's title, not the next rank's).
- Review rows are authority `list`, `film_id` NULL, `value` = `<slug>#<rank>`, reasons `unresolved` / `corpus-veto` / `duplicate-entry` / `tombstoned-holder` / `key-collision` / `entry-changed` / `id-disagreement`. They drain with `review resolve --film` / `--create` / `--dismiss` ONLY (design §1 A1) — `--pick/--tt/--none` key a FILM, and a list entry has none, so they are refused. `--film` links the entry to an existing film (refused when that film already sits at another rank on the same list), `--create` mints an unkeyed film from the entry's own `title_listed`/`director_listed` and the next sync keys it, `--dismiss` is a permanent standing decision. Resolution re-reads the entry from `film_list_entry` rather than trusting the row's stored `value`, and BOTH `--film` and `--create` refuse outright when the entry already carries a link to some other film. That refusal is reachable, not theoretical: `queue_list_review_once` dedups on reason + value, so ONE entry can accumulate two open rows under two reasons (an `unresolved` row from one run, a `corpus-veto` row from the next), and resolving the second would silently MOVE the link — `add_claim` is `INSERT OR IGNORE` on `UNIQUE(authority, value)`, so the first film would keep the `list` claim for an entry it no longer holds and nothing anywhere would record the move. A wrong link is silent where a duplicate film is not, and this one would happen AFTER the scorecard was printed. `id-disagreement` is a `list`-authority row exactly like the other reasons above it — `application/review.py`'s `list` branch matches on `authority == LIST_AUTHORITY and value is not None`, reason-agnostic, so it drains through the same `--film`/`--create`/`--dismiss` verbs with no reason-specific code, and `--pick`/`--tt`/`--none` are refused on it for the same reason as every other list row: no `film_id` to key.
- A list carrying IMDb ids (supplied-id spec §3, migration 014's `tt_listed`) is EXTERNAL GROUND TRUTH, not a shortcut: `reconcile` (supplied-id spec §5) runs the SAME resolver on every entry regardless of whether an id was supplied, and only then compares the two answers — the resolver is never skipped just because the file already names a tt. A `match` on the SAME tt is `agree` and proceeds down the ordinary linked/would-create path. A `match` on a DIFFERENT tt is `id-disagreement` — never linked, never created, always a review row, even where gate 1 would have linked the entry outright a moment before; two independent sources disagreeing about identity is exactly what a human is for. A non-`match` verdict with an id present proceeds on the SUPPLIED tt (`supplied`) — the id is evidence the resolver itself lacked. With no id at all, today's behaviour (pre-increment) is unchanged. The three gates plus 2b and gate 3's veto run UNCHANGED on every one of these paths, supplied id or not: a supplied id settles WHICH work an entry is, never whether the catalog already holds that work, which is the only question the gates answer and the only thing standing between this feature and a duplicate film. The resulting agreement rate is NEVER auto-ratified into `scripts/eval/thumbprint_eval_v1.csv` — `application/eval_log.py::ratify` is the only writer and only a human `review resolve` verdict drives it, or the matcher benchmark would be scoring itself; a disagreement becomes a review row a human can ratify through the existing path if and when they choose to.
- The scorecard (`scorecard`, design §7) is the DELIVERABLE of the accuracy test, not optional polish: a duplicate film announces itself, but a list entry attached to the wrong existing film does not, so EVERY entry gets its two-line block — the film it landed on, the gate that found it, and the resolver's own reason verbatim. Never abbreviate it to the exceptions. Both CLI verbs print it with `markup=False, highlight=False, soft_wrap=True`: a `[reason]` is text and not Rich markup, and the card is read as a file at least as often as on a terminal. Reason strings come from `resolve()` and are contract text — don't reword them. A list carrying at least one COMPARED entry (an id-bearing entry the resolver actually reached — never merely one with an id in the file: an entry already linked before the fetcher was touched, or whose every lookup failed, is skipped before `reconcile` and cannot be scored) gains one trailing tally line, `resolver vs supplied id:  agree A · disagree D · resolver had no verdict S  (of N compared)`, where `N = A + D + S`. It is the headline of a supplied-id import (supplied-id spec §2) — the point of running the resolver anyway is measuring it against ground truth it did not produce, for free, on every entry a list happens to carry an id for. The line is absent on a list carrying no ids, and absent on a run where every id-bearing entry was skipped before comparison.
- The read model fetches list membership for the WHOLE view in ONE query (`_LISTS_SQL` / `_lists_by_film`, the sibling of `_SERVICES_SQL`), never per film, and a membership count is NEVER denormalized onto `films` — `film_list_entry` is the single source of truth, and a stored count would go stale the moment a merge re-points an entry. `FilmView.lists` entries are `{slug, name, curator, published, ordered, trust, rank, rank_label, size}` and the drawer renders them as the "On lists:" row, showing the rank (label-or-position, tied-ranks design §4) only when the list is `ordered`. `size` (on-sale canon design §2/§9) is the list's FULL entry count — `(SELECT COUNT(*) FROM film_list_entry e2 WHERE e2.list_slug = e.list_slug)`, a correlated subquery inside `_LISTS_SQL` itself, not a second query and not a column denormalized onto `films`, for the same reason the tally is never stored there. It counts entries the import has not yet linked to any film, on purpose: `canon_score` (`domain/filters.py`) needs the poll's own published length as its denominator — how high a film sits relative to the WHOLE poll — not our coverage of it, which would shrink the denominator mid-import and inflate every already-linked entry's score as the rest of the list caught up. `merge_film` re-points a loser's `film_list_entry` rows to the survivor like every other film-scoped table — which is why `film_rank_on_list` is `ORDER BY rank`: after such a merge one film really can hold two ranks of one list, and the guard must answer the same rank every time.
- Rehearse before live (design §12): the whole import is run end to end against a COPY of the live DB with `MOVIE_BRAIN_CONFIG_DIR` set on every command, the full scorecard is read by the owner, and only then does anything run live — `lists import --apply` first, `lists create --apply` as a separate confirmed step.
- `film_list.trust` (migration 016) is `INTEGER NOT NULL DEFAULT 1`, and the default is load-bearing, not incidental (trust design §2 T1): with every list at 1 the weighted tally is arithmetically identical to the raw count, so the feature ships inert and only diverges once the owner expresses an opinion — no list is ever silently worth zero. `0` is legal and means "still visible in the drawer, scores nothing," the boolean behaviour available inside the integer model.
- **Only `movie-brain lists trust [SLUG [N]]` writes that column.** `upsert_film_list` names `trust` in neither its `INSERT` column list nor its `ON CONFLICT DO UPDATE SET` clause (`infrastructure/database.py`), so a re-import — which is normal, it's how a list picks up newly created films — leaves a stored trust untouched; on first insert the column takes its own default. Reintroducing a reset there would take a deliberate, visible edit, not an incidental one.
- The tally is **computed, never denormalized onto `films`** (trust design §1, holding the original three §5.7 constraints): `FilmView.lists` carries the per-film rows and the count is `f.lists.length` client-side (`app.js`), so "how many lists" can change meaning later — weighted, filtered by trust, whatever — without a migration.
- The chip counts **lists, not weight** (trust design §7): a film does not silently leave the "on 2+ lists" shortlist just because one of its lists was downgraded. `MULTI_LIST` lives only in `domain/filters.py` and reaches the JS through `/api/config`; `_PREDICATES["multi_list"]`, `CHIP_PREDICATES.multi_list` in `app.js`, and the button in `index.html` stay in lockstep — a chip present in one and missing in another is a silent dead control.
- Trust is visible in exactly one place in the UI (trust design §6): it orders the drawer's "On lists:" row, trust descending then name, via `ORDER BY e.film_id, l.trust DESC, l.name, e.rank` in `_LISTS_SQL` — never the card badge, which stays the bare count (`3 lists`, `1 list` singular) precisely because a weighted number means nothing until trust values are set.
- `sight-and-sound-1992-critics` (trust 8, 10 entries) and `sight-and-sound-1992-directors` (trust 6, 12 entries) are two files, not one, because they are two electorates — the BFI's 1992 page published a critics' top ten and a directors' top ten separately and never combined them into one ranking, so there is no single "1992 list" to merge them into (on-sale canon design §11). Both carry the header key `source:`, parsed into `ListMeta.source_url` by `header.get("source")` (`infrastructure/listfile.py::parse_list_file`) — `source_url:` is NOT a recognized header key. `parse_list_file` validates only the keys it reads (`slug`, `name`, `ordered`, the required two); an unrecognized key like `source_url:` is neither rejected nor an error, it is simply never looked up, so the list would parse cleanly with `source_url` left `None` — a silent loss, not a loud one, which is exactly why the correct key is worth writing down here.
- `my-owned-tiers` (and every slug in `domain/rank.py::RANKER_LIST_SLUGS`) is written by the tier ranker's save, not by a list file: no `lists/<slug>.tsv` exists, `lists import` exits 2 on such a slug, and `Repository.replace_list_entries` (its writer) rewrites the slug's entries whole and linked — the one list whose entries are NOT append-only. `trust` is still owned by `lists trust` alone. `lists create` cannot mint a film for a ranker slug because its worklist is entries with `film_id IS NULL` and the ranker writes only linked entries, so the worklist is empty by construction.

## Moved from CLAUDE.md (2026-09-21)

- Curated lists (`film_list` / `film_list_entry`, migrations 013 + 014's `tt_listed`) are checked-in artifacts at `lists/<slug>.tsv`, parsed byte-for-byte (curly apostrophes, `…` and the source page's own typos all survive — the director is corroboration, never an exact key). `list` review rows carry no `film_id` and drain with `review resolve --film`/`--create`/`--dismiss` ONLY: `--pick/--tt/--none` key a film, and a list entry has none. `lists import` NEVER creates a film on any path, even with `--apply` — creation is `lists create`'s own confirmed run, which re-resolves and re-gates every entry rather than trusting the import's verdict. Three gates stand before any creation: gate 1 (a film already keyed to the winning IMDb id), gate 2 (a film holding the winning candidate's TMDB id), gate 2b (`find_by_imdb` on the verdict's tt when the winner is OMDb-only or fell outside the ranked top three, so gate 2 asked nothing) and gate 3 (`corpus_veto` — any catalog film RESEMBLING the entry's titles, a veto and not a matcher). The form ladder is fallback-only: a `match` on the primary form returns immediately and a later form can never override it. A supplied id (the file's optional 4th column, stored as `tt_listed`) is external ground truth, never a shortcut: the resolver still runs on every entry and the two answers are reconciled — same tt `agree`, a different tt is an `id-disagreement` review row that never links and never creates, no verdict proceeds on the supplied tt — with the gates unchanged on every path, and the agreement rate is reported, never auto-ratified into the eval CSV. List membership is fetched in ONE query for the whole view (`_lists_by_film`, the sibling of `_SERVICES_SQL`) and a count is NEVER denormalized onto `films`; `FilmView.lists` feeds the drawer's "On lists:" row, rank shown only when the list is `ordered`, and also the dashboard's **list picker** (`#list-picker`, app.js-only, URL state `list=<slug>`): it derives its options from the films payload rather than an endpoint, orders them the owner's own lists first (curator `me` — the ranker's "My Ranking", 2026-09-14 ruling) then trust-desc then name, labels each `name (size)` — the list's own `name` from the file header, which the owner writes to read well here (`BFI: 100 Film Noir`) and which is unique by construction, where the earlier `curator published` form collided on the two 1992 Sight & Sound polls; the drawer's "On lists:" row uses the same name — and on selection filters to the list, orders by printed rank (unordered lists fall through to the default hierarchy) and touches no other control (since 2026-09-07; before the chip redesign it forced the scope to `all` — with every filter off by default that job is gone, and a Reachable chip the owner set stays set). Its `<select>` deliberately carries class `picker`, NOT `chip`: the `#chips` click handler matches `.chip` and would add `undefined` to the chip set.
- A list file's column one is the rank AS PRINTED, not the addressable position — ties are supported (`=243` for a critics'-poll tie), `film_list_entry.rank` is the entry's line order and stays what's addressable, and migration 015's `rank_label` stores the printed cell only when it differs (`cahiers-100.tsv`/`bergan-100.tsv` print `1..100` in order, so both store `NULL` throughout); see `.claude/rules/lists.md` for the full contract.
- **Old ratings** (spec `docs/superpowers/specs/2026-09-19-old-ratings-design.md`, migration 026): the owner's 1–5★ ratings from 2004–08 are a WATCHING SIGNAL — rewatch an old 5★, avoid an old 1★ — and never a rating: nothing reads `old_rating` into `my_ratings` or the ranker (a 2005 5★ → 10 would seed tier 1). One row per SOURCE LINE, PK `(source, line)`, title verbatim with its typos; `film_id` is a nullable but ENFORCED foreign key (`PRAGMA foreign_keys = ON`), NULL meaning only "the resolver has not placed this row yet", and deliberately not unique (the source lists one film twice). The `oldratings` verbs are the only writers. The key is assigned by the resolver and the list gates, never a title join: `application/old_ratings.py` is the SECOND caller of `application/lists.py`'s `resolve_entry` / `find_holder` / `corpus_veto` / `_key_new_film`, reused as they stand (each row rides as a `ListEntry` with its typed year as the listed year) — not abstracted, there is no third caller. Three deliberate differences from the list verbs: no `match_review` rows (a refusal stays `film_id NULL` on the scorecard and `oldratings link` is the hand path), no duplicate-entry block (two rows may link one film), no `claim` rows. `oldratings import` NEVER creates; `oldratings create` mints only rows rated `MINT_MIN_STARS` (4) or better and re-gates every one; `create_by_hand` (`oldratings create --line N --tt ttNNN`, 2026-09-20 — spec §6 had deferred it) is the same creating path for one row whose IMDb id the owner supplies, under the same star floor and the same gates; `absent` is a resolved 1–3★ work the catalog lacks, linked by a later re-run the day sync or a list brings it in. `FilmView.old_rating` = `{stars, rented_on}` or None, one query for the whole view (`_old_rating_by_film`, latest rental wins when a film holds two rows); the drawer shows `Me, 2004–08: ★★★★★ · rented …` under My rating, the row badges only the two ends (`.badge-old-loved` 5★, `.badge-old-avoid` 1★), and the plain **Rewatch** chip (`rewatch`, after On a list) is old 5★ AND unrated today — a pending request a rating serves, the "Rank this" rule again. There is no hide-1★ filter (7 films when built). `merge_film` re-points the rows (a plain UPDATE, not survivor-wins); `summary()` gained `old_ratings_linked` / `old_ratings`. The source CSV lives outside this repo and the tests use invented rows; the owner ruled the same day that the list is NOT private, so naming one of its titles here is not a leak.
