# Curated-list contract (spec `docs/superpowers/specs/2026-08-28-curated-lists-design.md`,
  seed `docs/superpowers/specs/2026-08-28-curated-lists-seed.md`)

- The failure this feature must not produce is a DUPLICATE FILM (seed §0). A list entry is a curator's title plus, usually, a director — no year, no id, no url — so every helper here is deliberately timid: under-creating costs one review row a human drains, over-creating costs a merge. Whenever a gate is unsure, it refuses and queues; it never guesses.
- Two verbs, two deliberate yeses. `movie-brain lists import PATH [--apply]` (`import_list`, design §5) links what the catalog already holds and asks about the rest, and **never creates a film — not on any path, not with `--apply`**. `movie-brain lists create SLUG [--apply] [--yes]` (`create_films`, design §6) is the ONLY path in this feature that creates one, behind its own confirmation. Both are dry-run by default and a dry run writes NOTHING — no registry row, no entries, no claims, no review rows. Both verbs need BOTH an OMDb key and a TMDB token (`session_fetcher` needs both to build a fetcher at all, and a missing token would silently disable gate 2b), and `lists create` checks that BEFORE it prompts: a run that cannot happen must not first ask the owner to authorise it. `create_films` itself refuses outright (exit 1, nothing touched) when handed `tmdb=None`, because gate 2b is not optional on the creating path — the invariant lives in the module that does the creating, not only in the CLI. `import_list` is deliberately left alone: linking without gate 2b is degraded, not dangerous.
- The list file (`lists/<slug>.tsv`, design §4) is a checked-in artifact, extracted once by hand — no scraper, no per-site selectors. `infrastructure/listfile.py::parse_list_file` is pure and keeps titles and directors BYTE-FOR-BYTE: curly apostrophes, `…`, and the source page's own typos (`Howard Hawkes`, `Joseph Mankiewitz`, `Ernst Shoedsack` in `cahiers-100.tsv`) all survive verbatim. A list is a historical record of what the curator wrote; the resolver matches on title and treats the director as corroboration, never as an exact key, so a typo is not a defect to fix. Header block is `# key: value` before the first data row (`slug`/`name` required, `ordered` defaults true); data rows are `rank<TAB>title<TAB>director`. `read_list_file` is the one I/O function.
- The form ladder (`resolve_entry`, design §1 A2) is FALLBACK-ONLY: the primary form is asked first and a `match` there returns immediately — a form further down the ladder can never override an already-corroborated primary match. Only when the primary misses are `base` and then each alt title tried, stopping at the first `match`. When nothing matches, the PRIMARY form's verdict is what comes back (it was asked against the title the curator actually wrote, so its reason is the one worth reviewing), or the first form that answered when the primary's own lookup failed; when every lookup failed, `(None, primary_form)` — a transient failure is not a verdict and must never become a durable review row. The query year is always `None`: the list carries no years and inventing one misleads the resolver. `entry_forms` is the ONE definition of "what might this entry be called?", shared by the ladder in both verbs. Gate 3 asks a DIFFERENT question — "what will the catalog GAIN?" — and **both** verbs veto over the entry's forms PLUS the winning candidate's own titles, through the one shared `veto_forms(forms, winner)`. The two questions stop having the same answer the moment phase 2 mints the film under TMDB's title rather than the curator's: a legacy unkeyed row titled like the winner holds no ids (gates 1/2/2b all miss it) and is titled nothing like the listed entry (the listed forms miss it too), leaving `films.key` — which refuses only when title AND year both match — as the sole backstop. The two vetoes are deliberately IDENTICAL and must stay so: `import_list` creates nothing either way, so the wider veto there only moves an entry from `would-create` to `blocked` plus a review row, and it moves it onto the rehearsal card the owner authorises FROM rather than leaving the card promising a creation the confirmed run would refuse. Strictly in the refusing direction, the same argument design §1 A4 makes for gate 2b. (The asymmetry between the verbs is the `tmdb is None` guard below, and only that.)
- Three gates before any creation, plus gate 2b (design §5.5, §1 A4). Gate 1: a film already keyed to the winning IMDb id. Gate 2: a film holding the winning candidate's TMDB id. Gate 2b: when gate 2 asked nothing — the winner is OMDb-only and carries no TMDB id, or `resolve` truncated `ranked` to three and the winner fell outside it — `tmdb.find_by_imdb(verdict.tt)` supplies the mapping and the holder is looked up on that. Gate 2b's only input is `verdict.tt`, never the winner. Gate 3 (`corpus_veto`): every catalog film RESEMBLING any of the entry's forms, which is a veto and not a matcher — a weak, ambiguous or tied hit is reason enough to refuse, deliberately inverting `owned import`, where the corpus matcher is a fallback that picks a winner. `find_holder`'s labels (`imdb tt…`, `tmdb N`, `tmdb(find N)`, `tombstoned #N`, `no holder`, `tmdb lookup failed`, `""`) are contract text the scorecard prints and callers branch on. A gate 2b RAISE is `error`, never `would-create`: the holder is unknown, not disproved, and calling it a would-create points phase 2 at a film that may already exist.
- `create_films` re-resolves and re-gates EVERY entry — phase 1's verdict is never trusted, the same re-derive-at-resolution-time rule the repair verbs follow. Its worklist is every entry with no `film_id` and NO `list` review row for its `<slug>#<rank>`, open or resolved: either kind means a human owns that entry. A film is minted under the WINNER's title and year (TMDB's own), with the listed title kept verbatim in the `claim` row, and is keyed immediately through `key_film` — born keyed, exactly as Mode-B promotion does it. A keying failure never undoes a creation that already happened; the next sync retries. Two consequences of that, both intended and neither obvious: (a) `list` is NOT in `application/thumbprint.py::_CLAIM_PRECEDENCE`, so a `list` claim never drives `film_query` — a list-created film that fails keying is re-queried by the next sync under its OWN (the winner's) title, not the curator's, and a reader of `thumbprint.md`'s "every ingester writes its own claim row at ingest" should not assume the claim participates in resolution; (b) `_key_new_film` SWALLOWS `key_film`'s `[partial]` `RuntimeError` where `repair editions` and `repair nomatch` raise and exit 1 — the deliberate exception to `thumbprint.md`'s loud-stop rule, because one entry must not abort a 100-entry run, and it is safe because the only non-`KEYED_OK` result is `id-conflict` and `record_tmdb_match` has already queued a durable `id-conflict` review row naming the twin before raising. Beyond the three gates, creation refuses on a tombstoned `films.key`, on a `films.key` collision `create_film` reports (never adopt the clashing film — that is how a wrong link is made), and on a `tt` this same run already minted (`minted`, which the gates structurally cannot stand in for: an unkeyed new film holds no external ids and is indexed under the winner's title, not the next rank's).
- Review rows are authority `list`, `film_id` NULL, `value` = `<slug>#<rank>`, reasons `unresolved` / `corpus-veto` / `duplicate-entry` / `tombstoned-holder` / `key-collision`. They drain with `review resolve --film` / `--create` / `--dismiss` ONLY (design §1 A1) — `--pick/--tt/--none` key a FILM, and a list entry has none, so they are refused. `--film` links the entry to an existing film (refused when that film already sits at another rank on the same list), `--create` mints an unkeyed film from the entry's own `title_listed`/`director_listed` and the next sync keys it, `--dismiss` is a permanent standing decision. Resolution re-reads the entry from `film_list_entry` rather than trusting the row's stored `value`, and BOTH `--film` and `--create` refuse outright when the entry already carries a link to some other film. That refusal is reachable, not theoretical: `queue_list_review_once` dedups on reason + value, so ONE entry can accumulate two open rows under two reasons (an `unresolved` row from one run, a `corpus-veto` row from the next), and resolving the second would silently MOVE the link — `add_claim` is `INSERT OR IGNORE` on `UNIQUE(authority, value)`, so the first film would keep the `list` claim for an entry it no longer holds and nothing anywhere would record the move. A wrong link is silent where a duplicate film is not, and this one would happen AFTER the scorecard was printed.
- The scorecard (`scorecard`, design §7) is the DELIVERABLE of the accuracy test, not optional polish: a duplicate film announces itself, but a list entry attached to the wrong existing film does not, so EVERY entry gets its two-line block — the film it landed on, the gate that found it, and the resolver's own reason verbatim. Never abbreviate it to the exceptions. Both CLI verbs print it with `markup=False, highlight=False, soft_wrap=True`: a `[reason]` is text and not Rich markup, and the card is read as a file at least as often as on a terminal. Reason strings come from `resolve()` and are contract text — don't reword them.
- The read model fetches list membership for the WHOLE view in ONE query (`_LISTS_SQL` / `_lists_by_film`, the sibling of `_SERVICES_SQL`), never per film, and a membership count is NEVER denormalized onto `films` — `film_list_entry` is the single source of truth, and a stored count would go stale the moment a merge re-points an entry. `FilmView.lists` entries are `{slug, name, curator, published, ordered, rank}` and the drawer renders them as the "On lists:" row, showing the rank only when the list is `ordered`. `merge_film` re-points a loser's `film_list_entry` rows to the survivor like every other film-scoped table — which is why `film_rank_on_list` is `ORDER BY rank`: after such a merge one film really can hold two ranks of one list, and the guard must answer the same rank every time.
- Rehearse before live (design §12): the whole import is run end to end against a COPY of the live DB with `MOVIE_BRAIN_CONFIG_DIR` set on every command, the full scorecard is read by the owner, and only then does anything run live — `lists import --apply` first, `lists create --apply` as a separate confirmed step.
