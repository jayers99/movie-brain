# Power search contract — credits, grammar, semantic stage (moved from CLAUDE.md 2026-09-21)

- Credits (power-search Plan A, migration 018): `person` / `film_credit` / `film_keyword` / `film_text` / `tmdb_facts` are the search data, written ONLY by `enrich credits` through `write_credits` (one film, one transaction, rows replaced whole; it also inserts the film's `tmdb_facts` row when none exists — with TMDB's real `alt_titles`, never a placeholder, because that row is the audit's facts cache — and stamps `credits_fetched_on`) and moved by `merge_film` on the survivor-wins rule. `person` is NOT an identity — `tmdb_person_id` is a join, not a `KEY_AUTHORITY`, and nothing here touches keying or matching. Names are ROWS, not a payload, because the owner's spelling requirement needs `person_fts` (FTS5 `trigram`) to correct a misspelled name BEFORE the query runs; a bare trigram MATCH is a SUBSTRING test, so misspelling lookups are an OR of the query's trigrams (`domain/search.py::trigram_query`). The three FTS indexes are external-content tables kept in step by migration 018's triggers — never write to them directly; `INSERT INTO x(x) VALUES('rebuild')` rebuilds one. Only `film_keyword_fts` tokenizes with `porter unicode61` (030); `film_text_fts` stays `unicode61` (owner decision 2026-09-23 — prose Porter cost verbatim recall); Porter has no `-ian` rule (`dystopian`/`dystopia` do not unify — the ladder's job). `job`/`department`/`character` are `NOT NULL DEFAULT ''` so the UNIQUE dedups (two NULLs are distinct to SQLite). Keywords are stored and, since 2026-09-23 (search-recall spec D2), matched through their own Porter index `film_keyword_fts` (migration 030) — a standalone FTS5 table, not external-content, because `film_keyword` has no INTEGER PRIMARY KEY; 30% of films still have none (D10). `keyword:` is now phrase CONTAINMENT through the stemmed index, not equality — `keyword: war` matches "star wars" and "world war ii" — and a quoted `keyword:` value is stemmed too (quoting means "no correction", not "no stemming"), while a `plot:`/text value is not, because the prose index is not stemmed.
- Power search (Plan B): `domain/search.py` is the pure grammar (`parse_query`: bare run-to-next-field values, quotes legal never required, unknown field → freeform + hint), similarity (`similarity`/`rank_candidates`: token-aware difflib with a named `LENGTH_PENALTY_EXPONENT` (0.35) so a short query embedded in a long name is not over-rewarded — measured `bogrt`→Humphrey Bogart 0.853, `bogrt`→Lena Brogren 0.593 — tiebreak on credit count then name; given the caller's floor (`_pick` passes `SUGGESTION_FLOOR`, `keyword_ladder` passes `FREEFORM_KEYWORD_FLOOR`) the candidates are prefiltered by difflib's upper bounds `real_quick_ratio`/`quick_ratio` over the whole name and each length-penalised token — lossless, and it took the 11,949-keyword ladder from ~150–190 ms to ~25 ms) and the `Filter` type; `application/search.py::run_search` resolves every fuzzy field to EXACT values before any query runs — exact match first, then trigram candidates ranked in Python, the top used only above `CORRECTION_FLOOR` (0.8) and ALWAYS reported in `corrections`, below it `suggestions` and an empty result (D7); a quoted value is exact and never corrected; `title:` is the one fuzzy-looking field that never corrects — it always applies its own substring filter and only ever offers the nearest titles as suggestions when it matches nothing. An unresolvable value inside a repeated field is `0 = 1` *inside its own OR group* (`_filter_sql`'s person/character/keyword/year branches all guard on it) — it never empties the whole AND'd result, so `actor: bogart actor: bacalllzz` still returns Alpha rather than nothing. `Repository.search_films` groups a field's clauses on `(kind, credit_kind, jobs)` — OR within a group, AND across groups, over the whole catalogue (never a post-filter over a top-N, D6) — and scores freeform text across `film_text_fts` (bm25 title 10 / overview 2 / plot 1), `person_fts` (5 for a cast credit billed in the top five, half for six to ten, nothing deeper, never crew — `FREEFORM_LEAD_BILLING`/`FREEFORM_MAX_BILLING`; measured on `marlowe`, 16 of 19 name hits were bit parts or crew, so a freeform name hit is the billing line, while `actor:` stays exact and complete), `character_fts` (4), genre (3), keyword (3, through `film_keyword_fts` as one `fts_phrase`, and when the stem finds nothing the ladder at `FREEFORM_KEYWORD_FLOOR` 0.9 — never both, so a hit is never double-counted) and a direct `films.title` LIKE (10, so never-enriched films are still found by title): every signal that matches is SUMMED per film, title-weighted — never a precedence where an earlier signal shadows a later one. The FTS trigram index is a candidate GENERATOR only — its own rank is never trusted (on the live index `bogrt` ranks "Ogranya" first). `GET /api/search?q=` returns `{ids, ranked, corrections, suggestions, hints, total}`; `hints` also carries two silent-empty explanations from `run_search` — a fuzzy value too short to correct (`'xy' is too short to correct — try three characters or more`) and a freeform miss on 2+ words (`no film matches all N words — try fewer, or quote a phrase`). `app.js` keeps `state.search = {ids, rank}` and intersects in `rowMatches`, ranks in `compare` only when `ranked` and no column sort is set, encodes `q=` in the URL, and marks `#search[data-settled]` when a response is applied (tests wait on it). The input is `#search.search`, OUTSIDE `#chips`, never `.chip`. Crew-job sets per field live in `FIELDS` and were verified against the live vocabulary 2026-09-06. Known limit: plot text exists only for enriched films (`film_text` is written by `enrich credits`).
- Semantic search (Plan C, spec D14–D21): migration 019's `film_embedding` (`film_id` PK, `model`, `dim`, plain BLOB `vector`, `embedded_on`) holds one vector per film over PROSE ONLY — `embedding_text` joins the non-empty overview/plot/tagline (never the title, D15) — as a plain BLOB rather than sqlite-vec, because brute-force cosine over the whole catalogue measured 0.08 ms per query (D14). `application/search.py::_semantic_stage` runs stage 4 in ONE mode (search-recall spec D3–D5, superseding D16/D18): the `SEMANTIC_NEAREST` 10 nearest films under `SEMANTIC_CEILING` 0.8 always join the result — a word hit keeps its lexical score plus `SEMANTIC_WEIGHT` 5 × (1 − distance) (D17 summed, a title hit at 10 stays first), a film reached by meaning alone carries the bonus only and is APPENDED after every word hit, never merged by score, and must pass every field filter over the whole catalogue; and no film is added at all when any word hit is a TITLE hit (`Repository.title_hits`: the `{title}` column of `film_text_fts` or the `films.title` LIKE — owner ruling 2026-09-23, so `maltese falcon` returns the film alone), though meaning still re-scores the word hits. The net is a count, not a distance, so it means the same under every model. Three hints are verbatim contract text: `"no exact match — showing the {n} closest by meaning"` (words found nothing), `"{n} more by meaning"` (words found something and meaning added n), and `"semantic search is not installed — uv sync --extra semantic"`. The model (`all-MiniLM-L6-v2`, 384 dims) lives behind the optional `semantic` extra (`uv sync --extra semantic`); `numpy` is a dev dependency so the suite always has it, torch is never imported by the test suite, and the one `@pytest.mark.semantic` test is the sole place that loads the real model. `create_app(repo, today, embedder=None)` builds a `VectorIndex` only when handed an embedder, lazily loading and rebuilding its matrix whenever `Repository.embedding_stamp` changes (`(count, max embedded_on, Σ film_id)` over non-disposed rows, so an out-of-process `embed --apply`, merge or tombstone is noticed on the next search) — and inside `create_app` that local is named `vector_index`, not `index`, because `index` already names the `/` route function in the same scope. `dashboard` passes an embedder only when `SentenceTransformerEmbedder.available()` is true, so the "not installed" hint is the real path when the extra is absent, and `SemanticUnavailable` is reserved for a model that IS installed but cannot load (not cached, offline) — a failed load is latched for the process and never retried. `merge_film` moves `film_embedding` survivor-wins like every other one-row table. `Repository.summary()` (shown by `movie-brain status`) gained `embeddings` (`embedding_summary()`'s count) and `prose` (`prose_count()`, `film_text` rows) keys. Known limit: the model rewards specific nouns over genre slang — `hard boiled private eye` ranks The Maltese Falcon 30th.
- `service:` (alias `on:`, 2026-09-22): films holding a CURRENT listing on a registered `movie_service`, **subscribed or not** (owner ruling — the name is explicit, so `service: mubi` must answer rather than return nothing). The resolver matches the registry's name or slug exactly (case-insensitive), else runs the keyword ladder over `Repository.service_candidates()` (key = slug, weight = current listings) — corrected above `CORRECTION_FLOOR` and shown, suggested below it; quoted is exact. "Current" is `_LISTING_CURRENT`, the ONE currency predicate now shared with `_SERVICES_SQL`: Criterion at its own latest `last_seen`, a TMDB-fed source at `tmdb_providers_refreshed_at` with the source's MAX(last_seen) as the pre-stamp fallback — a departed film never matches. Repeated `service:` terms OR by construction. No `app.js` change: the id set is the whole interface.
