# Sync flow (moved from CLAUDE.md)

1. Fetch browse-page token, then the cheap check: reuse the stored catalog if the last full walk is ≤7 days old, the API `total` equals the `films_raw_total` meta, and every page-1 key matches; otherwise full walk.
2. A full walk runs `merge_yearless()` first — Criterion publishes duplicate year-less pages (`…/film-title-1`) that must fold into their titled twin, or dupes resurrect every walk.
3. `record_catalog` upserts films (generating a `guid` for new ones), records each film's `criterion` external id, writes a `criterion` claim row inline against its own open cursor (the resolver reads the claim's ingested title/year, not `films.title`), and bumps listings `last_seen`; `set_leaving` maps "Leaving <date>" categories.
4. Offline Mode-B promotion (`promote_top_n`, meta `mc_top_n` — default 100, resolve-first since T5): `match_archive` runs first as the dedup guard (staged Metacritic titles claimed by an existing film are skipped; a fetcher resolves the title first and lands on the film already holding the resulting IMDb/TMDB id instead of creating a twin), then the remaining top-N staged titles become real films (generated guid, `clean_title`, MC year, director `NULL`) and each write a `metacritic` claim row; key-conflict and slug-conflict anomalies queue to `match_review` (never overwrite); archive shortfall (fewer staged titles than N) is logged with a crawl-more-pages hint; own tripwire — never affects exit code or later steps; no scraping (archive-only, offline). When a TMDB token is present, sync passes a shared `TmdbArbiter` into `promote_top_n` → `match_archive` → `match_film`, so a commerce-year gap (e.g. a US re-release year) auto-resolves against the original film instead of queueing `year-gap`; the arbiter talks only to the TMDB API (never metacritic.com) and any TMDB failure degrades to the old year-gap review — promotion never breaks on TMDB weather. The offline `metacritic match` CLI verb never gets an arbiter. With no fetcher (no TMDB token or no OMDb key), promotion behaves exactly as it did before the resolver switch.
5. Keying (`application/keying.py::key_films`, T5 — runs BEFORE the OMDb loop): every film in `films_needing_tmdb_match` (movies only — `kind='series'` films are excluded) is resolved through `film_query` + the session fetcher; a resolver `match` is written through `key_film` (holder checks before any write; a post-write `record_tmdb_match` failure outside `matched`/`adopted`/`collision` logs `[partial]` and raises); a non-`match` verdict writes ONE durable `no-match-reviewed` row carrying the A/B/C candidates (`queue_review_once` — idempotent, sync no longer mints plain `no-match` rows); a `held` id (twin) queues a durable `id-conflict` row instead of overwriting. With no fetcher (needs both a TMDB token and an OMDb key) the step logs and returns a no-op result — nothing is keyed. The whole step is wrapped in a try/except in `sync()`: a keying failure is logged and swallowed so it never breaks the OMDb or TMDB steps that follow (same one-source's-weather rule as every other sync step).
6. OMDb loop over `films_needing_lookup` plus `films_needing_lookup_discovery` (Mode-B films with no Criterion listing, queued after criterion-current films; their `Film.url` is the Metacritic movie URL) — fetched BY IMDB ID ONLY (`OmdbClient.lookup_by_imdb`; the `t=` title search is gone). A film with no `imdb` external id is skipped and counted in `SyncResult.omdb_unkeyed`, re-entering the queue at zero API cost every run until keying resolves it — so with no TMDB token nothing is keyed, and with nothing keyed nothing gets an OMDb record: enrichment is downstream of identity by design. Tripwires: a catalog failure leaves the DB untouched; OMDb quota exhaustion or 5 consecutive failures stops lookups but keeps progress (paid OMDb plan — quota exhaustion is a safety net, not an expected path).
7. TMDB provider step (token at `<config_dir>/tmdb-read-token.txt`, else skipped) — matching is no longer here (that's step 5 now); this step is availability only. A nightly watchlist provider pass (~50 films, every sync, never touches the weekly stamp), then a nightly first-check pass (up to `FIRST_CHECK_BATCH`=500 matched films with `providers_checked_at IS NULL` — a film matched after the weekly refresh must not wait a week with no listings; baseline semantics, no transitions; the full refresh skips anything checked today), then a weekly full US watch-providers refresh writing `listings` rows per service (never `criterion`), skipping films already checked that day, stamp written only on completion; own tripwires — TMDB failures never affect exit code or other steps. Listing writes (both the Criterion walk and TMDB provider passes) record `availability_transitions` against the pre-batch currency frontier — an insert or a stale-row reappearance fires an event, a current-row re-upsert stays quiet; a film's first-ever TMDB provider check writes listings WITHOUT a transition event (baseline, not arrival) — later checks fire transitions as normal; store-kind sources never fire "New on"/notifications (`_NEW_ON_SQL` is svod-only) but ARE surfaced in `FilmView.services` with `kind: store` (drawer "Buy on:" line + CheapCharts link — matrix-param URL `/us/search;q=<title>;t=all`; the site ignores a `?q=` query string). If ≥1 watchlist film transitioned today, one summary macOS notification fires at the end of sync (`infrastructure/notify.py`, injected as `notifier`; failures never affect exit code).
