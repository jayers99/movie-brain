# Sync flow (moved from CLAUDE.md)

1. Fetch browse-page token, then the cheap check: reuse the stored catalog if the last full walk is ≤7 days old, the API `total` equals the `films_raw_total` meta, and every page-1 key matches; otherwise full walk.
2. A full walk runs `merge_yearless()` first — Criterion publishes duplicate year-less pages (`…/film-title-1`) that must fold into their titled twin, or dupes resurrect every walk.
3. `record_catalog` upserts films (generating a `guid` for new ones), records each film's `criterion` external id, writes a `criterion` claim row inline against its own open cursor (the resolver reads the claim's ingested title/year, not `films.title`), and bumps listings `last_seen`; `set_leaving` maps "Leaving <date>" categories.
4. Offline Mode-B promotion (`promote_top_n`, meta `mc_top_n` — default 100, resolve-first since T5): `match_archive` runs first as the dedup guard (staged Metacritic titles claimed by an existing film are skipped; a fetcher resolves the title first and lands on the film already holding the resulting IMDb/TMDB id instead of creating a twin), then the remaining top-N staged titles become real films (generated guid, `clean_title`, MC year, director `NULL`) and each write a `metacritic` claim row; key-conflict and slug-conflict anomalies queue to `match_review` (never overwrite); archive shortfall (fewer staged titles than N) is logged with a crawl-more-pages hint; own tripwire — never affects exit code or later steps; no scraping (archive-only, offline). When a TMDB token is present, sync passes a shared `TmdbArbiter` into `promote_top_n` → `match_archive` → `match_film`, so a commerce-year gap (e.g. a US re-release year) auto-resolves against the original film instead of queueing `year-gap`; the arbiter talks only to the TMDB API (never metacritic.com) and any TMDB failure degrades to the old year-gap review — promotion never breaks on TMDB weather. The offline `metacritic match` CLI verb never gets an arbiter. With no fetcher (no TMDB token or no OMDb key), promotion behaves exactly as it did before the resolver switch.
5. Keying (`application/keying.py::key_films`, T5 — runs BEFORE the OMDb loop): every film in `films_needing_tmdb_match` (movies only — `kind='series'` films are excluded) is resolved through `film_query` + the session fetcher; a resolver `match` is written through `key_film` (holder checks before any write; a post-write `record_tmdb_match` failure outside `matched`/`adopted`/`collision` logs `[partial]` and raises); a non-`match` verdict writes ONE durable `no-match-reviewed` row carrying the A/B/C candidates (`queue_review_once` — idempotent, sync no longer mints plain `no-match` rows); a `held` id (twin) queues a durable `id-conflict` row instead of overwriting. With no fetcher (needs both a TMDB token and an OMDb key) the step logs and returns a no-op result — nothing is keyed. The whole step is wrapped in a try/except in `sync()`: a keying failure is logged and swallowed so it never breaks the OMDb or TMDB steps that follow (same one-source's-weather rule as every other sync step).
6. OMDb loop over `films_needing_lookup` plus `films_needing_lookup_discovery` (Mode-B films with no Criterion listing, queued after criterion-current films; their `Film.url` is the Metacritic movie URL) — fetched BY IMDB ID ONLY (`OmdbClient.lookup_by_imdb`; the `t=` title search is gone). A film with no `imdb` external id is skipped and counted in `SyncResult.omdb_unkeyed`, re-entering the queue at zero API cost every run until keying resolves it — so with no TMDB token nothing is keyed, and with nothing keyed nothing gets an OMDb record: enrichment is downstream of identity by design. Tripwires: a catalog failure leaves the DB untouched; OMDb quota exhaustion or 5 consecutive failures stops lookups but keeps progress (paid OMDb plan — quota exhaustion is a safety net, not an expected path).
7. TMDB provider step (token at `<config_dir>/tmdb-read-token.txt`, else skipped) — matching is no longer here (that's step 5 now); this step is availability only. A nightly watchlist provider pass (~50 films, every sync, never touches the weekly stamp), then a nightly first-check pass (up to `FIRST_CHECK_BATCH`=500 matched films with `providers_checked_at IS NULL` — a film matched after the weekly refresh must not wait a week with no listings; baseline semantics, no transitions; the full refresh skips anything checked today), then a weekly full US watch-providers refresh writing `listings` rows per service (never `criterion`), skipping films already checked that day, stamp written only on completion; a lookup that FAILS inside any of the three passes carries the film's then-current TMDB-fed listings forward to today with no transition (`Repository.carry_listings_forward`, backlog 13 — no answer is not a departure: a pass only aborts on five failures IN A ROW, so a scattered failure lets the stamp advance, and without the carry the failed film read as departed for a week and its next successful check fired a false arrival; already-stale rows and the Criterion row are never carried; a **404** on the providers call is an ANSWER, not weather — TMDB deleted the record, so the film is stamped checked with no providers, its rows go stale like any dropped service, it is logged once per refresh and never counts toward the five-in-a-row tripwire); own tripwires — TMDB failures never affect exit code or other steps. Listing writes (both the Criterion walk and TMDB provider passes) record `availability_transitions` against the pre-batch currency frontier — an insert or a stale-row reappearance fires an event, a current-row re-upsert stays quiet; a film's first-ever TMDB provider check writes listings WITHOUT a transition event (baseline, not arrival) — later checks fire transitions as normal; store-kind sources never fire "New on"/notifications (`_NEW_ON_SQL` is svod-only) but ARE surfaced in `FilmView.services` with `kind: store` (drawer "Buy on:" line + CheapCharts link — matrix-param URL `/us/search;q=<title>;t=all`; the site ignores a `?q=` query string). If ≥1 watchlist film transitioned today, one summary macOS notification fires at the end of sync (`infrastructure/notify.py`, injected as `notifier`; failures never affect exit code).
8. The catch-up chain (`application/catch_up.py`, owner ruling 2026-09-20 — every film gets its full enrichment when it is added): credits → vectors → store ids → trailers, each the verb's own use case run with apply over its own worklist, each under its own tripwire. Handed in as `sync(catch_up=…)` by the CLI (a sync called without one runs none — which is what keeps the sync tests offline), run LAST, skipped on `--ratings-only`; a failure is logged and swallowed and never changes the exit code. `sync(skip_catalog=True)` is the after-add mode the film-creating verbs use: steps 5–8 only, `tmdb_step(weekly=False)`, no notifier.

## Moved from CLAUDE.md (2026-09-21)

- **Enrichment on add** (owner ruling 2026-09-20: "anytime a new film is added, a full enrichment should be run … that way our database doesn't have to continuously be scoured for missing sparse data"; migration 029). Identity, ratings and availability were always sync's own steps; `enrich credits`, `embed`, `cheapcharts resolve` and `enrich trailers` were each built "never in sync" because each one's FIRST run was a backlog of thousands — that ruling REVERSES those four contracts now that the backlogs are drained and every one of them is a worklist of the films added since. `application/catch_up.py::catch_up` is the chain — credits → vectors → store ids → trailers, the order load-bearing (the vector is made from the prose the credits call brings; Apple's preview is found by store id) — each step the verb's OWN use case run with apply under its own tripwire (one source failing never stops the others, nothing can change an exit code; no TMDB token skips credits and trailers, no semantic extra skips vectors, and the line says `skipped`). `sync()` takes it as `catch_up=` — a callable built by `cli._catch_up_chain`, so the application layer never constructs a CheapCharts client or loads the model, and a sync test that passes none runs none — and runs it LAST (after the provider step, before the notification), never on `--ratings-only`; `SyncResult.catch_up` carries the `CatchUpReport` and the CLI prints `caught up — credits: N · vectors: N · store ids: N of M · trailers: N of M`. `sync(skip_catalog=True)` is the AFTER-ADD mode: keying, OMDb, the provider watchlist + first-check passes (`tmdb_step(weekly=False)` never starts the catalogue's weekly refresh and never writes its stamp) and the chain, with no Criterion walk, no Metacritic promotion and no notifier; `cli._enrich_after_add(repo, created)` runs it after `owned import`, `lists create --apply`, `oldratings create --apply` and `review resolve --create` whenever a film was created (never changing that verb's exit code; no OMDb key prints `new films not enriched` and carries on), and `enrich all` is the same thing by hand. The store-id step is only affordable because a CheapCharts MISS is remembered: `store_lookup` (film_id PK, asked_on; `_ONE_ROW_TABLES`) is written by `resolve_itunes_ids` through `mark_store_asked` for an unmatched, ambiguous or held answer — an ANSWER with nothing in it, never a failed call and never on a dry run — and `films_needing_itunes_id` skips those films unless `retry_misses`; before it, every run re-asked all 2,262 store-less films, one paced search each, about an hour (backlog 22). Migration 029 SEEDS the table for films whose `imdb` external id dates from on or before 2026-09-07 and that hold no store id, because the September full passes had asked about exactly those (2,199 rows on the 2026-09-20 copy); films keyed since are asked on the next run. There is deliberately NO automatic re-ask of old misses (that would be the scouring the ruling ends): a film Apple starts selling later is found only by `cheapcharts resolve --retry-misses --apply`. Measured on a migrated copy 2026-09-20: the first run keyed 2, looked up 22, wrote 23 credits, 23 vectors, 14 store ids of 74 asked and 14 trailers; the second run found nothing to do. Known oddity, pre-existing: two films keyed by IMDb id alone (#5015, #5115 — TMDB has no record) sit on `films_needing_tmdb_match` for ever and are re-resolved and counted `keyed` on every run.
