# Best-source contract (design `docs/superpowers/specs/2026-08-29-canon-best-source-design.md`, plan `docs/superpowers/plans/2026-08-29-canon-best-source.md`)

- The question this feature answers is per-film and only per-film: **"what is the best place to watch this?"** The set-wide question ("which subscriptions earn their keep?") was answered once by hand in design §2 and is deliberately NOT a feature (C8) — re-deriving it is a throwaway script in `scripts/discovery/`, never a verb. Do not grow a portfolio or coverage-per-dollar feature here.
- **Four ranking keys, in this order and no other: `subscribed DESC, quality DESC, has_apple_app DESC, name ASC`** (`domain/watch.py::rank_key`). `subscribed` first because C3 is "watch it once on something already paid for"; `quality` second because C7/C9 make it the owner's hand-set judgement of a service's transfers — which restoration, correct aspect ratio, real subtitles — which no API exposes; `has_apple_app` third because C6/C10 make it a tiebreak and never a veto ("if it's available nowhere else, I'm fine with that option"), so it must sit BELOW quality or "has an app, poor transfer" would beat "no app, restored print"; `name` last, purely for stable ordering. `has_apple_app` is a separate column rather than folded into `quality` precisely so those two facts cannot silently cancel each other.
- **The monetization tier is NOT a key, on purpose (C2).** *"I don't think it makes any difference whether they're free or flat rate or have ads. I'm just interested in maximum coverage of the Canon."* `flatrate`, `free` and `ads` all mean "I can watch this", so a free-with-ads service carrying a better transfer must be allowed to win — that is the whole reason `s.kind DESC` was dropped from the old `_SERVICES_SQL` ordering. `kind` keeps only its DISPLAY-SPLIT job: `svod` fills the drawer's "Also streaming on:" row and `store` fills "Buy on:". **A `store` is never a watch option** — `watch_options` filters to `kind == "svod"`, because a storefront is a shop, not access, and a film you must buy is exactly the film this feature exists to find an alternative for.
- **`rank_key` sorts ASCENDING = best first** — it negates `quality` and maps truthy flags to `0`, so `sorted(options, key=rank_key)` needs no `reverse=`, and the smallest tuple is the winner. `_SERVICES_SQL`'s `ORDER BY l.film_id, s.subscribed DESC, s.quality DESC, s.has_apple_app DESC, s.name` must stay in LOCKSTEP with it, and `tests/unit/test_database.py::test_services_sql_order_matches_the_domain_ranking` is the guard. **That test is the ONLY thing that can catch a broken `ORDER BY` there**, because `best_source` re-sorts the entries independently through `rank_key` — a divergence would leave the badged winner correct while the drawer's list beneath it silently disagreed, which nothing else in the suite would notice. Never "tidy" one of the two orderings without the other, and never delete that test.
- **Criterion is re-joined at the ranking site, not in SQL.** `_SERVICES_SQL` carries `WHERE l.source != 'criterion'`; the Criterion listing reaches the read model through `_VIEW_SQL`'s own LEFT JOIN and surfaces as `FilmView.criterion` / `FilmView.departed` instead. So `watch_options(view, criterion)` appends a synthetic option built from the `criterion` `movie_service` row (`_criterion_option`, read ONCE per view build and not per film) when `view.criterion and not view.departed`. Criterion covers **88 of the canon's 200**, so a ranking blind to it answers the wrong question for 44% of the set. It carries `quality` and `has_apple_app` like any other service and sorts on the same four keys — no new data is needed.
- **Do not "simplify" that by removing the `!= 'criterion'` exclusion.** Three features read that query, and widening it would fan Criterion into the drawer's "Also streaming on:" row, into the `reachable` scope's service test, and into the `acquire` chip's gate all at once — the chip has a SEPARATE Criterion clause precisely because `_SERVICES_SQL` excludes it. Unifying the two is a follow-up with its own measurement, never a silent widening (design §5).
- **`movie-brain services` is the ONLY writer of `quality`, `has_apple_app` and `subscribed`** (`cli.py`'s `services` group → `Repository.set_service_quality` / `set_service_apple_app` / `set_service_subscribed`, each documented as the sole writer of its column). Both columns follow `film_list.trust`'s precedent exactly (migration 017, `quality INTEGER NOT NULL DEFAULT 1`, `has_apple_app INTEGER NOT NULL DEFAULT 0`): with every service at its defaults the ordering is today's plus a tiebreak, so the feature ships INERT and diverges only once the owner expresses an opinion. `quality 0` is legal and means "still a real option, ranks last" — the boolean behaviour available inside the integer model, pinned by `test_quality_zero_ranks_below_quality_one`. Migration 021 adds `search_url` (TEXT, NULL) under the same rule — `set_service_search_url` is its only writer, `register_provider` still names none of the four.
- **`register_provider` must NEVER UPDATE an existing `movie_service` row.** It runs on every sync, for every provider TMDB reports — thousands of calls a night — so an UPDATE there would silently overwrite the owner's judgement the moment TMDB renamed a provider. Both its statements are `INSERT OR IGNORE`, and neither names `quality`, `has_apple_app` or `subscribed` in a column list or an `ON CONFLICT DO UPDATE SET` clause. Reintroducing a write there would take a deliberate, visible edit; do not make it an incidental one.
- **`register_provider` raises `ValueError` on a name that slugifies to empty, and the caller skips such a provider before calling it.** Both halves are load-bearing: `service_slug("...")` can return `""` for an all-punctuation name, and `""` is a corrupt PRIMARY KEY onto which every later empty-slugging name would silently fold via `INSERT OR IGNORE`. The invariant lives at the point of creation (the repository) so it can never be written; the caller's own `service_slug(name) == ""` check logs and skips (`application/availability.py::_refresh_pass`) so one malformed provider name cannot abort a ~4,600-film pass. Removing either one loses something the other does not cover.
- **`best_source` is computed on every read and MUST NEVER be denormalized onto `films` (C11).** It costs two extra keys on an ORDER BY the whole-view query already runs, and a stored value would need a refresh verb and would go stale the moment a merge re-points a listing — the identical argument `.claude/rules/lists.md` already makes for the cross-list tally and a list's `size` ("computed, never denormalized onto `films`"). `FilmView.best_source` is filled at view-build time in `get_view`/`list_views` from the one `_criterion_option` read plus the film's own `services`.
- **Possession short-circuits the ranking.** `best_source(view, criterion, store)` returns the `apple-tv-store` registry row immediately when `films.owned` — an owned film is the best access there is, so it never competes on the four keys (owner decision, 2026-08-29: *"if i own it the best source should be iTunes"*). The store row is PASSED, never hardcoded, so the drawer shows the registry's own name; and it answers even when the film carries no store LISTING, which is not hypothetical — 38 of 858 owned films have none. Since the 2026-09-07 drawer redesign the drawer's *owned* line is fixed copy (`Owned on Apple TV ↗`, spec D6) whose href is `FilmView.apple_tv_url` (the Apple TV app's `com.apple.tv://` scheme on the film's iTunes id) when the film holds one, else the store template, else the tv.apple.com search; the registry name still governs every unowned winner (`Watch on <name> ↗`), and the card badge is unchanged. A `store` of None falls through to the ordinary ranking, so a caller that forgets it is degraded rather than broken. The store never enters `watch_options`: it is the best-source answer only, never a streaming option, and `_SERVICES_SQL`'s `kind='store'` rows keep feeding the drawer's separate "Buy on:" line as before.
- `_service_option(c, slug)` reads ONE registry row per view build, never per film, and is called exactly twice — `criterion` (filtered out of `_SERVICES_SQL`) and `apple-tv-store` (the owned answer). Adding a third caller inside a per-film loop would be a query per film across ~4,700 films.
- **An owned row is not badged with its source** (`app.js`: `f.owned ? null : f.best_source`). The row already carries the `owned` badge, and the best source of an owned film IS that purchase, so a second badge states the same fact twice.
- **The drawer shows the best `TOP_SERVICES` (3) and hides the rest behind a `<details>` disclosure** (`app.js`'s `collapse` helper, `.svc-more` / `.svc-rest`). Auto-registration means a film can carry dozens of services — measured over the live catalogue on 2026-08-29: 4.1 on average, 45 on *Carnival of Souls* — so printing them all made the line unreadable. The cap is a DISPLAY cap and never a filter: the entries are already in ranked order, so the three shown are the best three, and a service the owner rates badly is still there, sorted last, for the case they explicitly asked for — *"let's say there's some movie I want to watch and that's the only place it's available. Yes, I will forgo my quality concerns."* Never turn this into a `WHERE` clause; the day it drops a row is the day the drawer stops answering "where COULD I watch this".
- A closed `<details>` still holds its text, so a Playwright assertion about what is hidden must test VISIBILITY (`not_to_be_visible` on `.svc-rest`), never `not_to_contain_text` — the DOM text is present either way and a text assertion would silently pass on a broken disclosure.
- **The Amazon-channel exclusion is REVERSED, and that is accepted.** `migrations/003_multi_service.sql` still carries the comment *"Amazon-channel ids (1825, 201, 287) and GB BFI Player (224) deliberately excluded."* Auto-registration overturns it: TMDB files Amazon Channels as ordinary US `flatrate` providers, so the registry will come to hold `max` beside `max-amazon-channel`, `mubi` beside `mubi-amazon-channel`, and so on — **the same service under two identities, with a film's listings split between them.** This is ACCEPTED, not a bug to fix: design §4 asks for every provider TMDB reports to be recorded and for `subscribed` to decide everything downstream, and C2's maximum-coverage argument points the same way — the alternative is curating a provider allow-list by hand, which is the failure mode §3 measured (29 of 46 checkable canon films had US availability the old eight-provider map threw away). Migration 003's comment is now HISTORICAL, not current; read it as a record of what was true at v3. **`subscribed = 0` is what contains the duplication**, and that containment is the whole reason a duplicate is harmless: an Amazon-channel twin cannot reach the `reachable` scope (which tests subscribed services), cannot suppress or qualify anything at the `acquire` gate, and cannot outrank a real option, because `subscribed` is the first ranking key. It shows in the drawer's "Also streaming on:" row and nowhere else. Do not "clean it up" by re-introducing an exclusion list.
- **`_NEW_ON_SQL` and `watchlist_transitions_on` filter on `s.subscribed = 1`** as well as `s.kind = 'svod'`. They were effectively subscribed-scoped already — five of the seven svod services migration 003 seeded were subscribed, and only `mubi` and `bfi-player-classics` were not — and auto-registration is what breaks that: hundreds of services arrive at `subscribed = 0`, and each one's FIRST listing write fires an `availability_transitions` row. Without the filter the first sync after rollout swamps the new-arrival chip and the drawer's "New on:" line for `NEW_ARRIVAL_DAYS` (14) with services the owner does not subscribe to, and notifies them about arrivals they cannot watch. These two queries are downstream, and design §4's principle is that `subscribed` decides everything downstream. Guarded by `test_new_on_ignores_an_unsubscribed_service` and `test_watchlist_transitions_on_ignores_an_unsubscribed_service`.
- The winner needs no prose explanation attached to it: **the ordering IS the reason**, and the drawer badges the first entry. Inventing a per-film sentence would be precision neither C6 nor C7 asked for (design §5).
- Out of scope and settled (design §7): non-US regions · rental prices · any per-film quality lookup against a second availability source (C9, §5.1 — JustWatch's unofficial GraphQL and Watchmode both work mechanically and are both rejected: they add a second availability authority to reconcile against `listings` and would return the same 1080p for nearly every canon film) · any change to `canon_score` · a refresh-cadence change (C12 — `meta.tmdb_providers_refreshed_at` with `REFRESH_DAYS = 7` is a STALENESS gate, not a clock, so manual syncs do the right thing unattended; no new verb and never a launchd agent).
- **`best_source` carries `url`, resolved on every read by `watch_url(option, title)` and never stored:** the registry template with the percent-encoded title, else the listing URL (Criterion's own page — the option is rebuilt per film with `listing_url = row['url']`, never by mutating the shared registry dict — or TMDB's watch page), else None. `_SERVICES_SQL` gained two SELECT columns for this and NOTHING in its ORDER BY; `_row_to_view` strips `search_url`/`listing_url` (`_PRIVATE_OPTION_KEYS`) from every `services` entry so the list payload stays URL-free (drawer spec D10, `test_services_entries_never_carry_urls`).

## Moved from CLAUDE.md (2026-09-21)

- `movie_service` is the service registry (slug PK; kind `svod`|`store`; `subscribed`/`region` are data, and since migration 017 so are `quality INTEGER NOT NULL DEFAULT 1` and `has_apple_app INTEGER NOT NULL DEFAULT 0` — the owner's two hand-set ranking constants, written by `movie-brain services` and by nothing else, exactly as `lists trust` owns `film_list.trust`; at the defaults the feature is inert; migration 021 adds a third owner column, `search_url TEXT` NULL, same single writer, not a ranking key). `service_provider` groups TMDB provider ids per service, and `register_provider` auto-creates BOTH rows for any provider TMDB reports that the registry doesn't know, at `subscribed = 0` — `INSERT OR IGNORE` on both statements, naming none of the three owner columns, so a nightly sync can never overwrite a judgement; a provider name that slugifies to empty raises there and is skipped by the caller. `external_ids` maps films to per-authority native ids, PK `(film_id, authority, value)`; `UNIQUE(authority, value)` remains the dedup guard; tmdb/imdb are single per work by policy, claim authorities may repeat.
- Availability lives in `listings`: TMDB writes svod sources from `flatrate`, `free` and `ads` unioned (canon-best-source C2 — all three mean "I can watch this", and reading only `flatrate` threw away 29 of 46 checkable canon films' US availability), plus `apple-tv-store` from rent/buy provider 2; the weekly refresh is gated by meta `tmdb_providers_refreshed_at`. Migration 003's "Amazon-channel ids (1825, 201, 287) and GB BFI Player (224) deliberately excluded" comment is HISTORICAL: auto-registration reverses it, so the registry will come to hold `max` beside `max-amazon-channel` and the like — accepted, not a bug, because `subscribed = 0` contains a duplicate (it can't reach the `reachable` scope, can't move the `acquire` gate, and can't outrank a real option since `subscribed` is the first ranking key).
- `FilmView.best_source` is the single best place to watch a film today — the first entry of its ranked svod option set (`domain/watch.py::best_source`/`rank_key`), sorted `subscribed DESC, quality DESC, has_apple_app DESC, name ASC`. The monetization tier is deliberately NOT a key (C2), and a `store` is never a watch option. It is **computed on every read and never stored** (C11; the same argument `lists.md` makes for the cross-list tally). Criterion is re-joined into the ranking at the ranking site, from the `criterion` `movie_service` row read once per view build, because `_SERVICES_SQL` filters Criterion out (`l.source != 'criterion'`) and it reaches the read model through `_VIEW_SQL`'s own LEFT JOIN instead — Criterion carries 88 of the canon's 200, so a ranking blind to it would answer the wrong question for 44% of the set. The card badges the winner only when it is subscribed; the drawer links it either way: `best_source` carries `url`, resolved on every read by `domain/watch.py::watch_url` — the service's `search_url` template with the percent-encoded title filled in, else the listing's stored URL (Criterion's direct page, joined per film from `_VIEW_SQL`; TMDB's watch page for provider-fed services), else null. `_SERVICES_SQL` reads `search_url` and `l.url AS listing_url` onto the option dicts ONLY for that resolution; `_row_to_view` strips both (`_PRIVATE_OPTION_KEYS`) so `FilmView.services` entries stay `{name, subscribed, kind, quality, has_apple_app}` and the list payload never carries a URL (drawer spec D10). See `.claude/rules/watch.md`. `movie_service.quality` is a PRIOR over a service's whole catalogue and cannot express a per-title transfer: `observations/presentation.tsv` is the hand-kept log of (film × service) viewing verdicts that records those — no code reads it, and it exists so the eventual schema is designed against real rows. Intolerance (#3096) is its proof case: good on `justwatch-tv` (Cohen restoration), awful on `mgm-plus`, the same night. A single title never moves a service's dial in either direction.
