13. [ ] **Scattered-failure guard on the weekly provider refresh** — found 2026-09-01 while reading Radarr for borrowable algorithms. Radarr gates every destructive cleanup on `if (!listItemsResult.AnyFailure)` — *any* failed list fetch, not a run of them — because acting on a partial fetch looks exactly like the world having changed. movie-brain has the coarse version of that guard already: `tmdb_step` withholds the `tmdb_providers_refreshed_at` stamp whenever a pass aborts (`application/availability.py`). The gap is that a pass only aborts after `MAX_CONSECUTIVE_FAILURES` **in a row**, and `_refresh_pass` resets `consecutive = 0` on every success, so a scattered error rate never trips it: the stamp advances, and the films whose TMDB call quietly failed keep a `last_seen` behind the new stamp. Since "current" for TMDB-fed sources is `last_seen >= tmdb_providers_refreshed_at`, those films read as no-longer-current — they drop out of the default `reachable` scope, and their next successful refresh writes an `availability_transitions` row against a frontier that says they were absent, i.e. a false "New on:" arrival for a film that never left. **Verified:** the consecutive-counter reset, and that scattered failures cannot abort a pass. **Inferred, not verified:** the false-arrival consequence — write the failing test first. Candidate fixes, cheapest first: count failures per pass rather than consecutively and withhold the stamp above a threshold; or track the failed film ids and exclude them from the currency comparison; or (Radarr's own answer, strictest) withhold the stamp on any failure at all. Two further Radarr borrowings came out of the same read and are deliberately NOT filed here, being design work rather than a defect: typed rejection-reason enums for the thumbprint resolver (whose free-text `reason` strings are also the benchmark contract), and Radarr's split between what matched and what the match is worth (`ProfileFormatItem.Score`, summed per profile), which is the shape the per-title override in `observations/presentation.tsv` eventually wants.

The plumbing already exists: the correction-chip click handler in `app.js` sets `state.q`, mirrors it into `#search`, clears `data-settled` and calls `runSearch()`, and that is the whole path a person link needs — the query lands in the URL's `q=` like any typed search, so the filtered view is shareable and the back button undoes it. Two decisions to make in the spec. **Quoted or bare:** the drawer's Cast and Writer rows are still OMDb's comma-separated strings (`payload.Actors`, `payload.Writer` with its `(screenplay)` / `(novel)` suffixes to strip), while the search resolves names against TMDB's `person` rows, so the two spellings can drift (romanization, middle names, "Jr."); a quoted value is exact and never corrected, so drift returns nothing silently, while a bare value goes through the fuzzy stage and a visible correction above `CORRECTION_FLOOR` — bare looks right, and the correction line then tells the owner what was actually searched. **Scope:** search intersects with the scope toggle, so a director's filmography clicked from a Criterion film would show only the reachable part; the list picker is the one control that forces `all` on the user's behalf, and a person link probably wants the same treatment, or a hint saying how many are hidden. Known limit, not a blocker: only enriched films carry credits (`film_credit` is written by `enrich credits`), so a never-enriched film is invisible to `actor:` even when its OMDb cast lists the name. Natural companion to item 4 (richer drawer), whose fuller cast list would read from `film_credit` directly and make the spelling question disappear — if that ships first, build the links on it instead of on the OMDb strings.
