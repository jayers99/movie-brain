## What Phase 2 is (spec §12, D2, D13 — already decided, don't relitigate)

- **The problem it solves, in the owner's words:** "if I do hard boiled San Francisco private investigator, that should do a semantic search on description or plot or more verbose, full concept and sentence fields." Today `hard boiled private eye` returns 0 with the hint above, because freeform words are ANDed lexically — and AND stays (D6: the bar must never quietly widen); semantic is a RE-RANK, not a widening of the lexical set. Decide in brainstorming whether semantic also CONTRIBUTES candidates when the lexical set is empty (the owner's example needs it to) — that is the one real design question; the spec says "a fourth stage that re-orders the surviving id set", which as written cannot answer the owner's own example when stage 3 returns nothing.
- **Fields:** `tmdb_facts.overview` (39/40 films have one), OMDb `Plot` (in the `omdb` payload, also copied into `film_text.plot`), `tmdb_facts.tagline`. Person biography, reviews, translations are OUT (D12, §3.3).
- **Shape fixed by the spec:** embeddings per film over overview + plot + tagline; yt-brain's proven stack is `all-MiniLM-L6-v2` via `sentence-transformers` (~2 GB with torch) with `sqlite-vec` for storage; it MUST be an optional extra (`uv sync --extra semantic`) — the project has four runtime deps (`typer`, `rich`, `flask`, `requests`) and Plan B added none; without the extra, search degrades to today's lexical behaviour (yt-brain has the same fallback: `_text_search`). A distance floor, like yt-brain's slider (0.1–1.2, default 0.6). The `/api/search` contract does not change (D13); `search_films` returns `(id, score)` so a re-ranker slots behind it.
- **Prior art to read (yt-brain, `github.com/jayers99/yt-brain`, not cloned locally — clone into the scratchpad):** `src/yt_brain/application/embed.py` (`MODEL_NAME`, `embed_videos`: text = `title\ndescription`, `_to_blob`), `src/yt_brain/infrastructure/database.py::search_similar` (`SELECT youtube_id, distance FROM video_embeddings WHERE embedding MATCH ? ORDER BY distance LIMIT ?`, `_load_sqlite_vec`), `src/yt_brain/web/dashboard.py` `/api/search` (embeds the query with `app._embed_model`, packs with `struct`, `max_distance` filter). **Do NOT copy its post-filter design** (D6 — it post-filters field terms over a semantic top-N and silently drops matches). The live `~/.config/yt-brain/yt-brain.db` shows the sqlite-vec table layout (`video_embeddings`, `_chunks`, `_rowids`, `_vector_chunks00`).

## Open questions for the brainstorm (the spec leaves these to Phase 2)

1. Re-rank only, or also a candidate source when the lexical set is empty (the owner's example query needs the latter)? If both: how does the UI say which happened (the hint line exists for this)?
2. What text is embedded per film — overview + plot + tagline concatenated, or title too (yt-brain includes the title)? Films with no prose row: skip, or embed the title alone?
3. Where the embedding table lives: migration 019 with a sqlite-vec virtual table (requires the extension loaded on every `Repository` open — how does that degrade when the extra is absent?), or a plain BLOB column read into numpy — measure at 4,645 films × 384 floats (~7 MB) before choosing; brute-force cosine in Python may be fast enough to avoid sqlite-vec entirely.
4. A verb `movie-brain embed [--apply]` on the `enrich credits` pattern (resumable by a stamp; the model load is the slow part) — and whether the model is loaded lazily by the Flask app on first semantic query (yt-brain preloads).
5. The distance floor: a constant, a `/api/config` value, or the yt-brain slider? The owner's stated preference elsewhere is fewer controls; a constant with the hint line explaining "showing the 12 closest by meaning" may be enough.
6. Testing without the model: a fake embedder (deterministic vectors) for pytest; the real model only in an opt-in marked test.
